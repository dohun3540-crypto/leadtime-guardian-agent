# Ground Rules

## 1. 소통과 일정
- 매일 `완료 / 다음 작업 / 블로커`를 팀 채팅에 공유한다.
- 결정한 사항은 GitHub Issue 또는 docs에 적고 담당자, 마감, 완료 조건을 남긴다.
- 막히는 문제는 하루 이상 혼자 붙잡지 않고 공유한다.

## 2. Git 규칙
- 기본 브랜치: `main`; 기능 개발은 `feat/...`, 버그는 `fix/...`, 문서는 `docs/...`, 데이터는 `data/...`.
- 직접 main push를 피하고 PR 후 merge한다. 일정상 긴급 예외는 이유를 PR에 기록한다.
- 커밋 접두사: feat, fix, test, docs, data, refactor, chore.
- 공용 브랜치 강제 push 금지; PR은 작은 단위로 유지한다.

## 3. 코드 리뷰와 품질
- PR에 목적, 변경 내용, 실행 방법, 테스트 결과, 이슈 링크를 기록한다.
- 가능하면 다른 팀원 1명 검토 후 merge한다.
- PR 전에 `pytest -q`와 `ruff check .`를 확인한다.
- AI가 생성한 코드도 실행하고 검증한 사람이 책임진다.
- `main` 브랜치 보호는 저장소 설정에서 별도로 활성화한다.

## 4. 개발 환경
- Python 3.11 사용; 가상환경 .venv 권장.
- 공통 JSON 키, 날짜 형식(YYYY-MM-DD), 수량 단위, 스키마를 임의로 변경하지 않는다.
- 변경이 필요하면 이슈/PR에서 영향 범위를 기록한다.

## 5. 데이터와 보안
- .env, API 키, 실거래 문서, 개인정보는 커밋 금지.
- 공개 데이터의 라이선스/출처를 기록하고, 합성 데이터는 synthetic으로 표기한다.
- 정답 데이터는 입력 데이터로부터 독립적으로 작성하고 수정 이력을 기록한다.
- 원본 파일은 data/raw 폴더에 로컬로만 보관하며 공유 가능한 샘플만 커밋한다.
- 외부 이메일 발송/구매 확정은 사람의 명시적 승인 후 수행한다.

## 6. 완료 조건
- 기능이 재현 가능하고 테스트/수동 검증 증거가 있다.
- README 또는 docs에 실행 방법과 입력/출력 예제가 있다.
- 스키마 변경이 있다면 샘플·테스트까지 동기화한다.

## 7. 우선순위
필수 대회 산출물 → Studio 실행 안정성 → 검증 가능한 정확도 → 구매 대응 차별화 → 웹 UI/장식 순.
